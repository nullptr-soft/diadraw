# Зв’язки

Зв’язок — це лінія між двома елементами: виклик, потік даних, залежність. Як і елементи, зв’язки оголошуються один раз у блоці `model`, а відображаються в кожному поданні, де видно обидва кінці.

```
model {
  customer = person "Customer"
  shop = system "Shop" {
    web = container "Web app"
    db  = container "Orders DB"
    web -> db "writes" tech "SQL"
  }
  customer -> shop.web "places order"
}
```

## Стрілки

| Стрілка | Вигляд | Типове використання |
| --- | --- | --- |
| `->` | суцільна лінія з одним наконечником | виклик, запит, залежність |
| `-->` | штрихова лінія | асинхронний чи непрямий потік |
| `<->` | наконечники на обох кінцях | двобічний обмін |

Після цільового елемента можна вказати підпис і будь-які з `tech`, `tag`, `style` і `prop`, як і для елементів. На лінії діаграми показуються підпис і технологія.

## Закінчення та стилі ліній

Стрілка задає звичайний вигляд лінії. Для інших варіантів — відкритої стрілки, ромба, «воронячих лапок», крапкової, подвійної чи кривої лінії — задайте зв’язку стиль. Див. [Закінчення та стилі ліній](line-styles.md).

## Кінцеві точки й порти

Кінцева точка — це елемент, записаний так, як на нього посилаються з місця оголошення зв’язку: `web` усередині `shop { … }`, `shop.web` будь-де. Якщо елемент оголошує порт (`api = container { port http north }`), `api.http` прикріплює лінію до цього порту.

## Перепідключення лінії

Щоб спрямувати лінію до іншого елемента, клацніть її. На обох кінцях з’являться кружечки. Перетягніть один із них на інший елемент і відпустіть; під час перетягування елемент під вказівником підсвічується. Якщо відпустити кінець на порожньому місці або на елементі, якого лінія вже торкається, нічого не зміниться.

Текст змінюється лише там, де записано цей кінець:

```
web -> legacy "REST" tech "HTTPS"  // being migrated
```

після перетягування наконечника з Legacy API на API перетвориться на

```
web -> api "REST" tech "HTTPS"  // being migrated
```

Підпис, `tech`, теги, коментарі та стрілка не змінюються. Новий кінець записується найкоротшим посиланням, яке веде до елемента з місця оголошення лінії: `api` всередині `shop { … }`, `shop.api` за його межами. У рідкісних випадках, коли жодне ім’я в цій області не підходить (усередині `shop` елемент `shop.db` затінює верхньорівневий `db`), натомість переформатовується файл, про що повідомляє рядок стану.

Корисно знати:

- **Лише елементи, не порти.** Перетягування кінця на елемент прикріплює його до самого елемента. Щоб прикріпити до порту (`api.http`), відредагуйте текст. Якщо кінець уже прикріплено до порту й ви відпустите його на тому самому елементі, порт збережеться.
- **Контейнери також підходять.** Відпустіть кінець на рамці контейнера осторонь вкладених елементів, і лінію буде з’єднано з контейнером.
- **Без петель.** Не можна перенести кінець на елемент, де вже закріплено інший кінець.
- **Автоматично побудовані поданням лінії не можна перепідключати.** Коли подання приховує елемент, його лінії ведуть до найближчого видимого предка (неявний зв’язок). У тексті їх у такому вигляді немає, тому в них немає маркерів. Перепідключіть справжню лінію в поданні, де видно обидва кінці, або в тексті.
- **Скасування** (⌘Z або Ctrl+Z) повертає кінець на місце і в тексті, і на полотні, як і для будь-якої іншої правки на полотні.

Що відбувається з ідентифікатором лінії та посиланнями на нього, залежить від наявності імені. У наступному розділі описано ідентифікатори, а далі — [як на них впливає перепідключення](#як-перепідключення-впливає-на-ідентифікатори).

## Ідентифікатори зв’язків

Кожен зв’язок має ідентифікатор. На діаграмі його не видно, але інші частини DiaDraw використовують його для звернення до конкретної лінії:

- **Ручне прокладання маршруту.** Коли ви [перетягуєте точки згину лінії](fixed-views.md#згинання-ліній) на полотні або імпортуєте діаграму draw.io, форма лінії зберігається в поданні як `route "<id>" via …`.
- **Правки на полотні.** Вибір лінії, зміна підпису та видалення працюють за ідентифікатором, як і точкові зміни тексту, які полотно записує до файла.
- **Експорт SVG.** Кожна лінія малюється як `<g class="dd-edge" data-id="<id>">`, тому вебсторінка, тест чи таблиця стилів може знайти її, наприклад, щоб підсвітити `[data-id="checkout"]`.
- **Перегляд змін.** Зі сталим ідентифікатором порівняння версій показує, що «ця лінія тепер веде в інше місце», а не що одну лінію видалено й іншу додано.

### Похідні ідентифікатори

Якщо не дати зв’язку ім’я, його ідентифікатор утворюється з кінцевих точок: `web -> db` стає `web->db`, `web -> api.http` — `web->api.http`, друга лінія між тими самими елементами — `web->db#2`, наступна отримує `#3` і так далі.

Це зручно, але ідентифікатор залежить від кінцевих точок. Він змінюється, коли ви:

- **перепідключаєте лінію**: `web -> legacy` стає `web -> api`, а її ідентифікатор змінюється з `web->legacy` на `web->api`;
- **видаляєте попередню паралельну лінію**: якщо є `order -> billing` і друга `order -> billing`, видалення першої змінює ідентифікатор другої з `order->billing#2` на `order->billing`.

Коли ви змінюєте кінцеві точки в тексті, посилання на старий ідентифікатор перестають працювати: для `route` зі старим ідентифікатором з’являється повідомлення `Unknown relationship`, і задані вручну точки згину втрачаються. Під час перепідключення на полотні це виправляється автоматично (див. нижче).

### Іменовані зв’язки

Поставте перед зв’язком ім’я та `=`, щоб дати йому власний ідентифікатор:

```
model {
  web    = container "Web"
  api    = container "API"
  legacy = container "Legacy API"

  calls = web -> legacy "REST" tech "HTTPS"
}

view main {
  route "calls" via 200, 80
}
```

Тепер ідентифікатор завжди буде `calls`. Навіть якщо змінити лінію на `calls = web -> api`, маршрут діятиме й далі. Назвати лінію можна й на полотні: виберіть її й введіть ім’я в поле Name інспектора, і маршрути оновляться автоматично (див. [Як назвати зв’язок в інспекторі](element-properties.md#як-назвати-звязок-в-інспекторі)). Іменовані й неіменовані лінії можуть стояти поруч:

```
order -> billing "charge"
refund = order -> billing "refund" tag "async"
order -> billing "audit"
```

Їхні ідентифікатори — `order->billing`, `refund` та `order->billing#2`. Присвоєння імені одній лінії не перенумеровує інші.

Правила іменування:

- Ім’я — це ідентифікатор (літери, цифри та `_`; починатися з цифри не може).
- Воно використовується без змін навіть усередині елемента: `writes = web -> db` усередині `shop { … }` має ідентифікатор `writes`, а не `shop.writes`.
- Ім’я має бути унікальним серед зв’язків: друге `x = …` — помилка. Воно може збігатися з іменем елемента, бо елементи й зв’язки мають окремі ідентифікатори.
- Слова `group`, `port` чи `layout` допустимі як імена: за стрілкою DiaDraw розпізнає, що рядок описує зв’язок.

### Коли варто назвати зв’язок

Дайте зв’язку ім’я, якщо від нього залежить щось поза самою лінією:

- ви проклали або плануєте прокласти маршрут вручну;
- це одна з кількох ліній між тими самими двома елементами, які ви можете видалити чи переупорядкувати;
- ви плануєте перепідключати її при зміні архітектури, наприклад під час переходу з одного сервісу на інший;
- на неї посилається сторінка, тест чи таблиця стилів через експортований SVG.

Якщо це не ваш випадок, залиште зв’язок без імені: похідного ідентифікатора достатньо, а текст буде коротшим.

### Як перепідключення впливає на ідентифікатори

Коли ви перепідключаєте лінію на полотні:

- **Іменована лінія зберігає ім’я.** `calls = web -> legacy` стає `calls = web -> api`, а `route "calls" …` продовжує діяти.
- **Неіменована лінія отримує ідентифікатор із нових кінцевих точок:** `web->legacy` стає `web->api`, а всі `route` зі старим ідентифікатором отримують новий, тож точки згину залишаються з лінією.
- **Паралельні лінії перенумеровуються разом зі своїми маршрутами.** Якщо є дві неіменовані лінії `order -> billing` і ви перепідключаєте першу до `ledger`, ідентифікатор другої змінюється з `order->billing#2` на `order->billing`. Маршрут першої оновлюється на `order->ledger`, а другої — на `order->billing`, тож жоден не потрапить до чужої лінії. Це діє й у зворотному напрямку: якщо перенести лінію на пару елементів, між якими вже є пізніше оголошена лінія, остання отримає `#2`.
- **Лінія залишається вибраною** під новим ідентифікатором.

Коли лінія перепідключається, її маршрут зберігає точки згину. Їх було задано для попередніх кінців, тому лінія може тепер іти в обхід. Перетягніть точки згину ще раз або видаліть із подання рядок `route`, щоб алгоритм проклав лінію сам.

Маршрути — єдині місця в тексті, де вказується неіменована лінія, тому оновлюються лише вони. Сторінка, тест чи таблиця стилів, які знаходять лінію в експортованому SVG за `data-id`, перебувають поза файлом і не оновлюються. Якщо щось таке залежить від лінії, дайте їй ім’я.

### Ідентифікатори, які не можна записати як імена

Модель також можна завантажити з JSON або побудувати програмно, і тоді ідентифікатори зв’язків можуть бути недопустимими як імена (наприклад, `edge-1`). Під час виведення такої моделі в текст ці лінії записуються без імені, тож після повторного зчитування тексту отримують похідні ідентифікатори.
